# SMU — план приведения реализации к архитектуре v2

Дата: 3 октября 2026 года. Основание: `SMU_SITE_ARCHITECTURE_CODEX_V2.md` и аудит текущего кода.

## Цель и границы

Довести существующее приложение до связанной научной платформы: учёный → исследование/проект → результат → научная публикация → редакционная статья. Использовать одну базу Supabase и существующие слои Actions → Services → Repositories. Выполнять работу проверяемыми этапами; завершение отдельного этапа не означает завершения всего плана.

Изменения существующей схемы выполняются новыми миграциями. Ранее применённые миграции не переписываются. Для каждого этапа обязательны lint, typecheck, необходимые регрессионные тесты и production build. Применение миграций к рабочему Supabase и развёртывание фиксируются отдельно от локальной готовности кода.

## Решения по неоднозначностям спецификации

1. Порядок поставки: безопасность и целостность → полноценная CMS и связи → языки/поиск/SEO → каталог и кабинет → операционные модули. Разделы 86 и 88 исходного документа трактуются как перечни функций, а не два разных обязательства поставки одного модуля.
2. `in_review` — действующий код статуса review. Добавление `changes_requested` и `scheduled` выполняется отдельной миграцией без разрушительного переименования существующих данных.
3. Редакционные операции пользователя должны проверять текущую сессию и права в приложении и БД. Для статей/учёных использовать защищённые RPC с `auth.uid()`, проверками ownership/permissions и ограниченными grants. Service role оставить для Storage, cron и явно описанных доверенных операций; не считать RLS защитой запросов service role.
4. Изменение содержимого сбрасывает одобрение/публикацию и верификацию атомарно. Научный рецензент видит назначенные ему материалы; редактор с `edit_any` и правом review может проводить общую редакционную проверку.
5. Публичные адреса в конечной версии: `/[locale]/...`; прежние адреса должны перенаправляться с сохранением параметров. Slug находится в переводе и уникален внутри языка/типа сущности; история адресов не допускает перехвата старого URL другой записью.
6. Уведомления о заявках и результатах рассмотрения входят в операционный этап. Рассылки, Telegram и расширенная аналитика — следующий этап, не препятствующий запуску CMS.
7. Одобрение относится к версии содержимого. Preview доступен только по правам или временному токену. Публичные запросы явно проверяют статус, время публикации и soft delete независимо от административной сессии.
